# AJACE Timesheet — Direct++ on AWS

Employee timesheet capture with **Direct++** AI extraction: upload a timesheet
(PDF, image, Excel), the AI reads it, the employee corrects anything it missed,
and an admin reviews every submission against the original document.

**Runs on AWS and OpenRouter only.** No Supabase, no Vercel, no Python engine.
The only request that leaves AWS is the OpenRouter call that reads a document.

```
Browser ──HTTP(S)──► Caddy ──► Next.js 14 (:3009, pm2) ──► OpenRouter (Direct++)
                                    │
                     ┌──────────────┴──────────────┐
                     ▼                             ▼
            Amazon RDS Postgres              Amazon S3
            records + auth_users             file bytes
```

| Concern | How it works |
|---|---|
| **Auth** | Self-managed: `auth_users` + bcrypt, session = signed JWT in an httpOnly cookie (`lib/aws/auth.js`) |
| **Data** | RDS Postgres over `node-pg`; one scoped endpoint `/api/data` (`lib/aws/data.js`) |
| **Authorization** | Enforced in SQL per request — ownership is forced server-side, never trusted from the client |
| **Files** | S3, **proxied through the app** (`/api/storage/upload`, `/api/storage/get`) |
| **AI** | OpenRouter (`DIRECT_SERVERLESS=true`) — runs inside the Next app, no separate service |
| **Email** | Amazon SES for password resets (optional) |

> **Why there is no S3 CORS configuration:** the browser never talks to S3. Uploads
> and downloads are proxied by the app using the EC2 instance role, so there is no
> cross-origin request to allow and the box needs no `s3:PutBucketCORS`. If you see
> a CORS error, something is bypassing `/api/storage/*` — fix that, don't add CORS.

## Deploy

Two paths, same result. Both create: S3 bucket, RDS Postgres, EC2 host, IAM role,
security groups, and a $15/month budget alert.

**A. CloudFormation** (recommended — one stack to delete later)
```bash
aws cloudformation deploy \
  --template-file deploy/infra/cloudformation.yaml \
  --stack-name ajace-timesheet --capabilities CAPABILITY_IAM --region us-east-2 \
  --parameter-overrides VpcId=vpc-xxx AppSubnetId=subnet-public \
      DbSubnetIds=subnet-a,subnet-b KeyName=ajace-key SSHLocation=YOUR_IP/32 \
      DBPassword='a-strong-password' BucketName=ajace-ts-files-1234 \
      BudgetAlertEmail=you@example.com MonthlyBudgetUSD=15
```

**B. Plain AWS CLI** (no CloudFormation)
```bash
REGION=us-east-2 DBPASS='a-strong-password' BUDGET_EMAIL=you@example.com \
  bash deploy/scripts/aws-cli-deploy.sh
```
It discovers your default VPC/subnets, provisions everything, and prints the IP,
DB endpoint, and a ready-to-paste env block. Resource ids are saved to
`deploy/.aws-state` — **keep that file**, `aws-cli-destroy.sh` needs it.

**Then, on the box:**
```bash
ssh -i ajace-key.pem ubuntu@<AppPublicIP>
git clone https://github.com/RW2523/ajace-timesheet-aws.git
cd ajace-timesheet-aws
cp deploy/env.production.example .env.production
nano .env.production          # DATABASE_URL, STORAGE_S3_BUCKET/REGION, OPENROUTER_API_KEY
bash deploy/scripts/install.sh
```
`install.sh` is the whole setup: packages, build, schema migration, pm2, Caddy —
then it health-checks and prints the live URL. Re-run it any time to deploy
updates; it keeps the last good build and rolls back if a build fails.

**First admin:**
```bash
deploy/scripts/make-admin.sh you@example.com    # takes effect immediately, no re-login
```

## Configuration

Everything lives in `.env.production` at the repo root (see
`deploy/env.production.example`). The ones that matter:

| Variable | Notes |
|---|---|
| `DATABASE_URL` | RDS endpoint. TLS is on by default; `PGSSL=disable` only for local Postgres |
| `STORAGE_S3_BUCKET` / `STORAGE_S3_REGION` | **must** match the bucket you created, or every upload fails |
| `OPENROUTER_API_KEY` | Direct++ extraction |
| `AUTH_JWT_SECRET` | auto-generated by `install.sh`; production refuses to start with a placeholder |
| `COOKIE_SECURE` | `false` when serving plain HTTP on the raw EC2 IP, `true` once you have HTTPS |
| `SES_FROM_EMAIL` | leave commented out until the sender is verified and out of the SES sandbox |

`NEXT_PUBLIC_*` values are baked in at build time, so `.env.production` must
exist **before** the build (`install.sh` handles the ordering).

## Test

```bash
bash test/run.sh
```
Starts a throwaway Postgres in Docker, applies the real schema, and runs the
data-layer suite against it — jsonb round-trips, the manual-entry path, the admin
settings upsert, and the authorization rules that replace RLS (one employee must
never see another's hours, no self-escalation to admin, no SQL injection via
column names). Nothing touches AWS or real data.

## Day-2

| Task | Command | Where |
|---|---|---|
| App start/stop/logs | `deploy/scripts/app.sh {start\|stop\|restart\|status\|logs}` | box |
| Stop/start the box (save compute) | `deploy/scripts/instance.sh {start\|stop\|status\|ip}` | laptop |
| Deploy an update | `git pull && bash deploy/scripts/install.sh` | box |
| Nightly DB backup → S3 | `deploy/scripts/backup.sh` (cron) | box |
| Delete everything | `deploy/scripts/teardown.sh` (CFN) or `aws-cli-destroy.sh` | laptop |

> Stopping the instance assigns a **new public IP** on start unless you attach an
> Elastic IP. `install.sh` rewrites `SITE_URL` from instance metadata on each run.

## Security notes

- Plain HTTP on a raw EC2 IP is **unencrypted** — fine for a pilot with test data.
  Before real employee data: add a domain, uncomment the domain block in
  `deploy/Caddyfile` (Caddy issues the certificate automatically), and set
  `COOKIE_SECURE=true`.
- The RDS instance is not publicly accessible; only the app's security group can
  reach port 5432. SSH is restricted to the IP you pass as `SSHLocation`.
- S3 blocks all public access; files are served only through authenticated
  app routes that check ownership (owner, or an admin).
